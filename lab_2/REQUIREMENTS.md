# Проверка по методичке

Основание: раздел ЛР2 «Объекты и классы», страницы 3–4; общие требования, страница 1.
Прочитана вся методичка (12 страниц). Требования поздних лабораторных в ЛР2 не перенесены.

| Обязательный пункт | Где показать |
| --- | --- |
| Консольное приложение на C++ | `main.cpp`, функция `main` |
| Классы, атрибуты, методы | `Point`: `x_`, `y_`, `Move`, `Print` |
| Наследники | `ColoredPoint : public Point`, пустой `PlainPoint` |
| Конструкторы без параметров, с параметрами, копирования | У `Point`, `ColoredPoint`, `Circle`, `CirclePtr`; все вызваны в демонстрациях |
| Наследник без собственных конструктора и деструктора | `PlainPoint` — намеренное исключение для этого отдельного примера; компилятор создаёт неявные методы |
| Деструкторы | У четырёх основных классов; вывод виден при завершении блоков и при `delete` |
| `private`, `protected`, `public` | Поля Point закрыты; `PrintCoordinates` защищён; `Print`, `Move`, `GetX` открыты |
| Продемонстрировать ограничения доступа | Закомментированные запрещённые обращения в `PointDemo`; обращение к защищённому методу в `ColoredPoint::Print` |
| Методы внутри определения и за его пределами | `GetX` в `objects.h`, остальные — в `objects.cpp` |
| Локальные объекты | Например, `Point original(1, 2)` |
| Динамические объекты | `new Point`, `new ColoredPoint`, соответствующие `delete` |
| Списки инициализации | Например, `Point::Point(int x, int y) : x_(x), y_(y)` |
| Порядок конструкторов предка и потомка | `InheritanceDemo`: Point до ColoredPoint |
| Метод потомка с тем же именем, без `virtual` | `ColoredPoint::Print`, `Point::Print` |
| Вызов метода предка из метода потомка | `Point::Print()` внутри `ColoredPoint::Print` |
| Композиция с полем-объектом | `Circle::center_`, инициализация в списке; автоматическое уничтожение после тела `~Circle` |
| Композиция с полем-указателем | `CirclePtr::center_`, `new` в конструкторах, `delete` в деструкторе |
| Композируемые классы определены отдельно | `Point`, `Circle`, `CirclePtr` — отдельные классы, не вложенные |
| Сравнить оба вида композиции | Блоки 4 и 5, пояснение в `THEORY.md` |
| Копирование объекта и последующие изменения | `Point copy(original)`, `first = original`; независимость координат |
| Копирование указателя и последующие изменения | `alias = dynamic`; изменение через alias видно через dynamic |
| Копирование владеющего объекта | `CirclePtr copy(original)` создаёт отдельный центр; изменяются и оригинал, и копия |
| Указатель на базовый и на производный объект | `baseObject`, `view` в `InheritanceDemo` |
| Ограничение доступных методов по типу указателя | `base->Print()`, закомментированный `base->SetColor(3)` |
| Объект базового класса, созданный из потомка | `Point sliced = colored`, потеря добавленного цвета |
| Порядок деструкторов | Потомок до предка, содержащий объект до своих полей после тела деструктора |
| Отладочный вывод | Все явно написанные конструкторы и деструкторы, основные методы |
| Комментарии и единое оформление | Все три исходника |
| Git с историей со второй лабы | Локальный репозиторий, команда `git log --oneline --reverse` |
| Умение добавить поля и методы | Упражнения и решения в `THEORY.md` |

`GetX` и `PrintCoordinates` — короткие вспомогательные методы; отдельный отладочный
префикс у них не выводится. Их результат выводится вызывающим кодом.
Неявные конструктор и деструктор PlainPoint не содержат собственного вывода;
вызовы соответствующих методов Point видны.

## Что не добавлялось

Отдельный класс для агрегации, виртуальные методы, виртуальный деструктор,
конструкторы перемещения, умные указатели, `dynamic_cast`, шаблоны,
GUI и меню не нужны для покрытия заданий ЛР2.
Про агрегацию есть объяснение в теории, поскольку её могут спросить устно.

В методичке не рекомендуется строить примеры на перегрузке операторов.
Здесь нет собственных реализаций таких операторов: одна строка `= default`
разрешает обычное присваивание Point, а `= delete` запрещает опасное
присваивание CirclePtr. Оба случая отдельно объяснены в теории.
